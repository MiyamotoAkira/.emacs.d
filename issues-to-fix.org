* Bugs
** DONE Package archives are re-downloaded on every startup
CLOSED: [2026-10-15]
Found by timing each =README.org= section (2026-10-15). /Packaging/ took
*7.6–9.7s* of a 9–11s batch load; every other section was under 0.4s.
Measured on its own: refresh *1.9s* (network-dependent), reading the cached
archives *0.006s*.

*Real cause: the ELPA Org install in =init.el= never succeeds.*
=init.el= checks =(assq 'org package-alist)=, finds nothing, refreshes the
archives and calls =(package-install 'org)=. That answers "‘org’ is already
installed" because the built-in Org (9.8.7) counts as installed, so ELPA Org
(9.8.10 on GNU) is never installed. The check fails again on the next start,
so every startup downloads the archives. There is no =elpa/org-*= directory;
Org is loaded from =/usr/local/share/emacs/31.1/lisp/org/=.

The timing script didn't run =init.el='s install step, so the refresh showed
up under /Packaging/ instead. My first diagnosis (that commit =3dfd4a4= caused
it by removing =package-initialize=) was wrong: =init.el= runs before
=README.org=, so its refresh already happened before that commit.

- [X] Deleted the redundant refresh block in /Packaging/ (2026-10-15). After
  =init.el='s refresh the archives are always loaded, so it never fired. Dead
  code, no speedup: the config still refreshes once and loads in 3.3–3.6s
  (was 3.34s).
- [X] Fixed the Org step in =init.el= (2026-10-15). It now refreshes the
  archives and passes the archive's =package-desc= to =package-install=.
  With the symbol ='org=, =package-install= treats the active built-in Org as
  installed; with =package-install-upgrade-built-in= bound to =t= it refuses
  as well (=package.el= line 2130 in 31.1). Given the descriptor for an
  uninstalled version, it installs it.

  Result: ELPA Org 9.8.10 installed in =elpa/org-9.8.10/= and loaded from
  there, no "Org version mismatch" warning. Later startups don't refresh:
  batch load *3.3–3.6s → 1.4s*.

Other sections in the batch timing (GUI-only work such as fonts and posframes
isn't included): /OS/ (=exec-path-from-shell=) 0.33–0.39s, /Main Org Section/
0.19s, /Mode line/, /Vertico/, /org-roam/, /Python/ and =require org= about
0.13–0.15s each; everything else under 0.05s.

** DONE combobulate aborts every tuareg-mode hook
CLOSED: [2026-10-16]
Found while testing the two fixes above (2026-10-15). Combobulate is hooked
on =prog-mode=. In a tuareg buffer it calls
=(treesit-parser-create 'ocaml)=, which signals =treesit-load-language-error=
because no OCaml grammar is installed. =prog-mode-hook= runs before
=tuareg-mode-hook=, so the error stops all the tuareg hooks: Merlin,
merlin-eldoc, ocp-indent and opam-switch-mode are all off in OCaml buffers.
Emacs reports it as a "File mode specification error".

Verified: with =combobulate-mode= removed from =prog-mode-hook=, a =.ml=
buffer gets =opam-switch-mode=, =ocp-indent-line= and =merlin-mode=.

The same can happen in any non-tree-sitter mode for a language combobulate
knows but has no grammar for.

Fix options:
- Only enable combobulate when the buffer already has a tree-sitter parser,
  i.e. in =*-ts-mode= buffers.
- Hook combobulate on the specific =*-ts-mode= hooks instead of =prog-mode=.
- Install the OCaml grammar (doesn't fix other languages).
